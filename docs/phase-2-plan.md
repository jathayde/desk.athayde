# Phase 2 plan: propose and approve (shadow mode on)

Source of truth: `docs/artifacts/investment-copilot-prd.md` §5.1, §5.4, §5.4.1, §5.4.2, §5.5, §5.8, §5.8a, §6, §7, §8, §10; screens in `investment-copilot-ui-flows.md` Flows 2, 3, 6, 7, 8 and the wireframes. Phase 1 (`docs/phase-1-plan.md`) is deployed; its conventions hold (secrets in credentials, no plaintext account numbers, CUSIP identity, every "logged" action an `audit_events` row, no live Schwab calls in tests, unattended runs read-only, `bin/ci` green per step, DHH and counselors review per step). Equities only (PRD §8). Nothing auto-executes: the only path to Schwab's order endpoint is the operator's approve gesture in the Rails UI, and it stays shadowed until shadow mode is turned off deliberately. Revised after the counselors plan review (codex-5.5-high, claude-fable).

## 0. Decisions and assumptions

1. **Approve is the submission.** Flow 2's deliberate confirm is the moment the order goes to Schwab (or, in shadow mode, would have). There is no resting `approved` state that code can submit later: `OrderProposal#approve_and_submit!(user:, acknowledged:, override_reason:)` is one synchronous request; the operator waits for the outcome on the page. The word `approved` does not appear in the state list.
2. **Shadow mode stays on for the whole phase.** `SystemSettings#shadow_mode` is true by default; turning it off is a typed-confirmation toggle on the system page, audited (`shadow_mode_toggled`). In shadow mode the approve path runs end to end and the submission step audits `would_have_submitted` with the exact payload instead of calling Schwab; the proposal leaves the approvable states exactly as a real submission would. **Shadow reconciliation is defined:** the operator places the shadowed order by hand at Schwab, the sync ingests it as `schwab_direct`, and the same matcher the reconcile job uses (§5) links the `would_have_submitted` attempt to that order and diffs the payload against the shape Schwab returned. The system page counts shadowed approvals and how many reconciled cleanly; that count, not a number in this plan, is what the operator reads before turning shadow off. This exercises the matcher and the bracket shape before either guards money.
3. **Two halts, not one.** The kill switch (Phase 1's manual halt, Flow 8) stops everything: entries, exits, stop adjustments, tool proposals. A rule halt (daily loss, max drawdown; PRD §5.4 3) blocks new entries only; exits and tighten-only stop adjustments stay available. Rule halts are durable state on `system_settings` (`rule_halt_rule`, `rule_halt_reason`, `rule_halt_tripped_at`, `rule_halt_resets_at`), tripped by the evaluator or the nightly check with one `rule_halt_tripped` audit and one email, cleared at the reset time or by the operator with a reason. `SystemSettings#writes_allowed?` is replaced by `entries_allowed?` (no kill switch, no rule halt) and `exits_allowed?` (no kill switch); shadow mode is not a gate but the branch between `would_have_submitted` and a real call.
4. **Sizing is computed by Rails at proposal creation and frozen.** Quantity = floor(risk budget ÷ per-share risk), risk budget = the max-risk-per-trade rule's percent × equity from the latest fresh balance, per-share risk = entry − stop (both from the proposal; a zero or negative per-share risk, or a short-side entry, is a hard fail). Whole shares only. Entries are LIMIT orders only in Phase 2 (a MARKET entry has no price to size or collar against). Approval re-runs the rules over the frozen quantity; a context change that would have changed the quantity or turned a pass into a fail refuses with "re-propose", never a silent recompute. The agent proposes symbol, side, limit price, stop, thesis, setup; Rails fills the quantity and the collar.
5. **Bracket = Schwab `TRIGGER` strategy**: a LIMIT entry whose `childOrderStrategies` carries one `STOP` sell for the same quantity (`# SCHWAB_SHAPE_UNVERIFIED`: strategy type name, child shape, child status while the parent works, whether a `TRAILING_STOP` child is accepted). **An exit reduces or cancels the bracket child in the same approve step**: a sell proposal on a position with a working stop carries the child cancel or replace, so no oversized stop is left at Schwab. `Schwab::OrderPayload` (bracket, sell, replace_stop, cancel) lives in the Schwab namespace like every other shape; the proposal never spells a Schwab field name. `Schwab::Client#place_order` returns the order id from the `Location` header, `#preview_order` if the endpoint exists, `#cancel_order`, `#replace_order`.
6. **Idempotency is local (PRD §5.1) and survives a killed worker.** Two transactions, not one. First: lock the proposal row, verify the state and the gates, re-evaluate, move `validated → submitting`, insert the `submission_attempts` row with the payload, commit. Then the HTTP call with short explicit timeouts (5 s open, 20 s read, no retries). Second: record the outcome. Nothing re-enters an approvable state from `submitting` or `submission_unknown`. A `submitting` row older than the timeouts plus slack is swept to `submission_unknown` by the tick, never back. A 2xx without a parsable order id is `submission_unknown`. The broker order id goes on the proposal in the second transaction; the orders sync links the order and its child by that id, since Schwab carries no proposal id. Database invariants: at most one attempt per proposal whose outcome is not `failed` (partial unique index); `submitted` requires an attempt; `filled` and `cancelled` are written only by the sync.
7. **Reconciliation is conservative and locks the instrument.** `Submission::ReconcileJob` waits a quiet period (60 s), searches the orders endpoint for a match (account, instrument by CUSIP, side, quantity, order type, limit or stop price, session and duration, entered within the attempt window), excludes orders already linked to any proposal, treats two matches as ambiguous for the operator, and confirms a "nothing found" twice, ten minutes apart, before the proposal becomes resubmittable (`submission_failed`, with the attempt marked `not_placed`). While any proposal on an instrument is `submitting` or `submission_unknown`, every other proposal on that instrument hard-fails as "pending reconciliation", including the manual form and the tool. `submission_unknown` is a banner on the dashboard and the queue and an email, until resolved.
8. **Guardrails are data** in `risk_rules` (`rule_type`, `params`, `active`, `version`, `setup_id`, `superseded_by_id`, plus `mode` and `note`): edits create a new version and supersede the old, never update in place; one active row per `(rule_type, setup_id)` with `NULLS NOT DISTINCT`. `guardrail_results` snapshots each rule's id, version, and params with its outcome and numbers. Outcomes: `pass`, `caution` (needs acknowledgement; the wash-sale rule's `mode` uses the same word), `block`, `unavailable`, `skipped`. **Unavailable behaviour is defined per rule:** settled cash unavailable (stale balance, unverified mapping) is a hard fail; sector exposure (2b) and earnings and econ blackout (5) are unavailable in Phase 2 because there is no sector or calendar source (FMP is Phase 2.5) and are shown as a warning the operator must acknowledge on every entry, with the words "not checked". That is a deviation from PRD §5.4, which lists them as starting rules; it is recorded here for the user to confirm, and the rules become real when FMP lands.
9. **Settled cash (rule 4)** subtracts from the broker's settled cash every unfilled app buy in `submitting`, `submission_unknown`, or `submitted`, and every live broker buy order the sync knows, whether or not `cashAvailableForTrading` already nets working buys (verify-on-approval item 10 is open; double-subtract until it is verified). A balance past the staleness threshold makes the rule unavailable, and unavailable here is a hard fail.
10. **Stop collar (§5.4.1)** from Schwab daily history through `Agent::MarketData` (cached, budgeted): ATR(14) multiple, swing low over N bars minus a buffer, percent stop, chandelier (reference). Parameters per setup in `stop_collar` rules. Data quality: at least 30 daily candles, the latest within two trading days, a fresh quote, a positive per-share risk. Bad or missing collar data is a hard fail for entries (nothing to override); only a stop computed and outside the range is the overrideable `caution` with a logged reason. Rules 1 to 4 and 7 are hard fails.
11. **Wash sale (§5.4 6), both directions, taxable losses only.** On a buy in the taxable account: caution or block (the rule's `mode`) when the same CUSIP realized a loss in the taxable account within the prior 30 days. On a sell that would realize a loss: warn when the same CUSIP was bought within the prior 30 days in the taxable account or the IRA (the loss would be disallowed). An IRA buy inside 30 days after a taxable loss cannot be blocked (no proposals there); it is named on the trade and in the brief. Instrument match only, and the detail page says so. **Tax lots (6a):** every sell carries `tax_lot_method` (FIFO default; enum `# SCHWAB_SHAPE_UNVERIFIED`) and shows the open lots with short or long-term status from the journal's legs.
12. **Write tools exist only on the interactive transport** (`mcp: true, scheduled: false, read_only: false, audited: true`); the registry writes an `audit_events` row for every audited call: `propose_order`, `annotate_trade`, `add_watchlist_item`, plus the read tool `evaluate_hypothetical_order`. `submit_order`, `cancel_order`, `edit_risk_rules`, and token operations do not exist as tools.
13. **One approver.** `users.approver` boolean (seeded true for John); only an approver's session can approve, reject, override, edit rules, or toggle shadow mode; the second user reads. A second inbox is otherwise an order path.
14. **Notifications in Phase 2 are email** (new proposal, fill or cancel, halt tripped, unprotected position, submission unknown), one per event, audited, no dollar figures in subjects, deep links only; push replaces the time-sensitive set when the iOS shell exists.
15. **iOS: Rails side in this repo, shell in its own repository, last step of the phase.** PRD §6 lists the Hotwire Native app with push and Face ID in Phase 2; this plan delivers the Rails half (path configuration, device registration, APNs delivery) and defers the Xcode project to a separate effort. That is a scope deviation for the user to confirm. APNs needs a gem outside Rails defaults (candidate `apnotic`), a decision for the user.
16. **Every state change is an audit event** with the actor: `proposal_created`, `proposal_evaluated`, `proposal_approved` (acknowledged warnings, override reason), `proposal_rejected`, `proposal_submitting`, `proposal_submitted`, `would_have_submitted`, `submission_unknown`, `submission_reconciled`, `submission_failed`, `proposal_expired`, `proposal_filled`, `proposal_cancelled`, `rule_changed` (before and after), `rule_halt_tripped`, `rule_halt_cleared`, `shadow_mode_toggled`, `unprotected_alert_sent`, `agent_tool_used` (written after the call, with the outcome and the tool_calls id).

## 2. State table (step 0 of the build)

A written table, state × action × result, including the crash points, from which the transition specs are generated: creation → `proposed` → evaluate → `validated` or `rejected_by_rules`; `validated` → approve (lock, re-evaluate, `submitting`, attempt row) → HTTP → `submitted` (order id) or `submission_unknown` (timeout, 5xx, dropped connection, 2xx without an id) or `submission_failed` (4xx, attempt `failed`, the operator sees the error and may re-propose); `submitting` older than the timeouts → `submission_unknown` (sweep); `submission_unknown` → reconcile → `submitted` (found, linked) or `submission_failed` (confirmed absent twice, attempt `not_placed`) or stays with "ambiguous" for the operator; `submitted` → sync → `filled` or `cancelled`; `proposed` and `validated` → expire at the end of their market day; `validated` → reject (human) → `rejected`. Illegal transitions raise; every legal one audits.

## 3. Guardrail engine

`Guardrails::Evaluator.new(proposal).call` returns `Guardrails::Report` (a `Result(rule, outcome, detail)` per active rule; `blocked?`, `warnings`, `needs_override?`, `unavailable`) and is the only writer of `guardrail_results`. Rules are `Guardrails::Rule` subclasses keyed by `rule_type` over `Guardrails::Context` (fresh balance or its staleness, open positions and their risk, today's realized P&L and drawdown, the projected cash of §0.9, the instrument lock of §0.7, the wash-sale history, the collar): `max_risk_per_trade`, `max_positions`, `max_position_exposure`, `max_sector_exposure` (unavailable → acknowledge), `daily_loss_halt` and `max_drawdown_halt` (which also trip the durable rule halt), `settled_cash`, `earnings_blackout` (unavailable → acknowledge), `wash_sale`, `notional_cap` (per order and per day, counting today's `submitting`, `submitted`, and `filled`), `stop_collar`, `pending_reconciliation`. Evaluation runs on create and again inside the approve lock; `evaluate_hypothetical_order` runs the same evaluator over an unsaved proposal and returns the report without writing anything.

## 4. Stop collar, sizing, trails

`StopCollar::Calculator.new(instrument, entry_price:, setup:)` pulls one year of daily candles and the current quote, checks quality, computes every enabled method from the setup's `stop_collar` rule, and returns `Collar(methods:, tight:, wide:, floor:, quality:)`; the percent stop is the floor. `Sizing.for(proposal, equity:)` freezes the quantity and the numbers behind it into `sizing`. `StopCollar::TrailJob` (17:00 New York) recomputes chandelier and ATR trails for open positions into `positions.suggested_stop` for the EOD brief's "tighten stop" line; adjusting the real stop is a `stop_adjustment` proposal, tighten-only unless a human types a reason.

## 5. Proposals, approval, submission

`OrderProposal` kinds: `entry` (LIMIT buy with a child stop), `exit` (sell, with the child action), `stop_adjustment` (replace the working stop). Origin `agent` or `human`. `Proposals::Create` is the one service the tool and the form use (resolve the instrument, size, collar, evaluate, audit). The queue is `/proposals`, the detail `/proposals/:id` (Flow 2: the evaluation table with outcomes and numbers, the collar with the stop marked, the sizing, the thesis and setup, the lots on a sell, the warnings to acknowledge, the override reason field, the approve and reject forms; web confirm is a typed word; iOS later: Face ID). The manual form is `/proposals/new` (Flow 3), collar and sizing recomputed through a Turbo frame. `Submission::Submit` is the two-transaction path of §0.6 with the shadow branch; `Submission::ReconcileJob` per §0.7; `Submission::Sweep` in the tick; `Orders::ProtectionWatch` in the orders sync (a parent filled with no live child, or a working stop gone at the broker → the unprotected alert once per position, audited).

## 6. Wash sale and tax lots

`WashSale.check(instrument, side:, accounts:)` per §0.11 over closed trades (taxable losses) and fills in both accounts. `TaxLots.for(trade)` lists open entry legs with acquisition dates and terms.

## 7. Write tools and the registry

`Agent::Tool` gains `audited:`; `Agent::Tools.call` writes `agent_tool_used` with the tool name and arguments (never the account hash) for an audited tool. `ProposeOrder` (through `Proposals::Create`; refused during a rule halt for entries and during the kill switch for everything), `AnnotateTrade` (appends to the post-mortem), `AddWatchlistItem`, `EvaluateHypotheticalOrder`. `Agent::Tools.for(:scheduled)` cannot see a write tool by construction.

## 8. Rule editor, halts, watchlist

`/risk_rules` (Flow 6): one row per active rule, a form that creates the next version, an effect preview over today's positions and pending proposals, locked while any halt is engaged with the override path (engage the kill switch, type a reason, edit). Rule halts show on the dashboard banner (entries blocked, exits open) distinct from the kill switch. `/watchlist` (Flow 7): items from the tool and the form, a link to propose from each, and the morning brief's "watching" section reads the table.

## 9. Notifications and screens

`AlertMailer`: `new_proposal`, `fill_or_cancel`, `halt_tripped`, `unprotected_position`, `submission_unknown`. Proposal queue and detail, manual form, rule editor, watchlist, the shadow-mode and halt controls and the shadow reconciliation count on the system page, the dashboard's pending-proposals line and the unprotected and submission-unknown banners, the EOD brief's fills recap linking fills to proposals, the trade detail's originating proposal. Playwright: a warn, a hard fail, an override, an approve in shadow, a submission unknown, a rule halt with an exit still allowed.

## 10. iOS (Rails side)

`GET /native/path_configuration.json`, `POST /native/devices`, `Push::Deliver` behind the alert events with email as the fallback; the approve endpoint accepts the web's typed confirmation or the shell's signed confirmation header (`# VERIFY: Hotwire Native bridge contract`). **Built 2026-09-02 without the gem:** `GET /native/path_configuration` (the shell is pointed at that path; unversioned, since one build and two users re-read it on launch; a catch-all default rule, modals for forms and sign-in, pull to refresh only on the three mobile-first screens), `POST /native/devices` behind the normal CSRF protection (the shell submits the registration from the web view so the token rides along; a JSON caller without a session gets 401 and no return path is stashed), `Device.register!` with its `device_registered` audit (registered, or reassigned to the other user), and a layout that gives the shell the brand and a sign-out and never the web navigation, keyed on turbo-rails' `hotwire_native_app?`. **APNs (decided 2026-09-02: the Meticulous developer account, `apnotic`):** `Alert` is the one place an alert leaves the desk, sending the email and, through `Push::DeliverJob`, the same words to every registered device with the path the shell opens; a token Apple says is gone removes the device (`device_removed`); credentials under `apns` (`key`, `key_id`, `team_id`, `bundle_id`, optional `environment: sandbox`), and a production desk without them boots and sends no pushes. Still open: the signed confirmation header (verify item 63).

## 12. Schwab shapes to settle before step 4 (Phase 2 section of `docs/verify-on-approval.md`)

At zero risk, before step 4: place one bracket by hand on Schwab's site, let the sync ingest it, and read the strategy type, the child shape and status while the parent works, `taxLotMethod`, and the fields the order search can filter on and their time precision; probe `previewOrder`. Only the first live submission can settle the `Location` header, write rate limits, and replace semantics on a `TRIGGER` child: a one-share first-live runbook with the operator watching, after shadow reconciliation. The evaluator, collar, sizing, wash sale, queue, and mailer are safe to build and shadow before any of this.
