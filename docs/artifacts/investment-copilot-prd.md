# PRD: Investment Copilot (working title)

**Owner:** John Athayde
**Status:** Draft v9 (iOS app decided)
**Date:** 2026-08-15

## 1. Summary

A personal investment operating system for a Schwab taxable brokerage account. A Rails application acts as the system of record and the sole gateway to Schwab's Trader API. Claude acts as the analysis and workflow agent on top of it, via an MCP server the Rails app exposes. The human approves every order.

This replaces the "folder of markdown files + FMP connector" pattern with a real backend, while keeping the file-based memory layer as the strategy/context store the agent reads.

## 2. Goals

- Positions, balances, orders, and transactions synced from Schwab automatically. No hand-maintained portfolio.csv.
- A trade journal with per-setup expectancy stats that is populated from actual fills, not memory.
- A guardrail engine (risk rules as data, not vibes) that evaluates every proposed order before it can reach Schwab.
- Daily pre-market and end-of-day briefs generated by the agent from live synced data.
- Human-in-the-loop order flow: agent proposes, Rails validates, human approves, Rails submits.

## 3. Non-Goals (v1)

- Fully autonomous trading. No order reaches Schwab without explicit human approval.
- Multi-user / multi-tenant. This is single-operator software.
- Options strategies beyond the account's approved option level.
- Real-time streaming / intraday tick monitoring. Polling cadence is minutes, not milliseconds.
- Trading other linked accounts (read-only visibility into the IRA and any other accounts is in scope for wash-sale awareness; trading them is not).

## 4. Architecture

```
┌─────────────┐     MCP (tools)      ┌──────────────────────────┐
│   Claude     │◄────────────────────►│  Rails app ("Copilot")   │
│  (agent)     │                      │                          │
└─────────────┘                      │  - OAuth token lifecycle  │
      │                              │  - Schwab API client      │
      │ reads                        │  - Sync jobs (Solid Queue)│
      ▼                              │  - Guardrail engine       │
┌─────────────┐                      │  - Journal & analytics    │
│ memory files │                      │  - Order proposal queue  │
│ (git repo)   │                      │  - Approval UI (Hotwire)  │
└─────────────┘                      └────────────┬─────────────┘
                                                   │ HTTPS/OAuth2
                                                   ▼
                                     api.schwabapi.com/trader/v1
                                     api.schwabapi.com/marketdata/v1
```

**Why Rails and not just an agent:** the agent cannot be trusted with credentials, token refresh timing, idempotent order submission, or rule enforcement. Those are deterministic jobs. The agent is good at synthesis, briefs, screening, and post-mortems. Split accordingly.

**Why an MCP server and not the agent hitting Schwab directly:** one credential holder, one audit log, one place guardrails run. The MCP tool surface is the contract.

## 5. Components

### 5.1 Schwab Integration (Rails)

- **App registration:** Schwab Developer Portal, Trader API - Individual product. Manual approval, 1-3 business days. Callback URL must be HTTPS and match exactly.
- **OAuth:** three-legged OAuth 2.0. Access token ~30 min, refresh token hard-expires at 7 days with no programmatic renewal.
  - Background job refreshes the access token every ~25 minutes while a valid refresh token exists.
  - Re-auth flow: when the refresh token is within 24h of expiry, the app notifies (email/SMS/push) with a one-click link to redo the browser login. Track refresh-token age as a first-class health metric on the dashboard.
  - All scheduled work checks token health first and degrades gracefully (queues, does not silently skip).
- **Account numbers:** call `/accounts/accountNumbers` first; use encrypted account values for all subsequent calls. Never store or log plaintext account numbers.
- **Client generation:** the api-evangelist OpenAPI specs turned out to be skeletal (minimal order schema, no response schemas for chains), so treat them as scaffolding only. Better references for the real shapes: the schwab-py order-builder docs and community client libraries that model the full schema; replace with Schwab's official schemas once portal access is approved. Wrap in a thin service layer with retry/backoff and rate-limit awareness.
- **Secrets:** app key/secret in Rails credentials; tokens encrypted at rest (Active Record Encryption). Nothing broker-related in the memory files repo.
- **Order submission idempotency:** the Schwab order POST has no client-supplied order id (per community clients; confirm post-approval), so dedupe is local. The approved → submitted transition runs under a row lock and is the only code path that can call the order endpoint. On an ambiguous outcome (timeout, 5xx, connection drop after send), the proposal enters `submission_unknown`; a reconciliation job queries the orders endpoint for a matching order (instrument, qty, side, price, time window) before any retry. No blind retries, ever.

### 5.2 Data Model (core tables)

- `accounts` (encrypted hash id, type: ira/taxable, trading_enabled boolean)
- `instruments` (CUSIP as the stable key; current symbol, symbol history, asset type, leveraged flag). Every other table references instrument_id, never a raw ticker, so ticker changes cannot break linking.
- `positions` (account, instrument, qty, cost basis, synced_at): always broker-derived
- `orders` (broker order id, status, side, instrument, qty, type, limit/stop, placed_via, parent_order_id for bracket children; see 5.4.2)
- `order_proposals` (agent- or human-initiated; status: proposed → validated/rejected → approved → submitted → filled/cancelled; stores guardrail evaluation results as JSON; carries a submission_attempt record for the ambiguous-outcome path in 5.1)
- `transactions` (fills, dividends, corporate actions, fees)
- `trades` (journal). A trade is one instrument's position lifecycle from zero back to zero; scale-ins and scale-outs are `trade_legs` linked to transactions. Fields: setup tag, thesis, planned stop/target, realized R-multiple, post_mortem. Fills with no originating proposal (orders placed at Schwab directly) create a trade in `incomplete` state with no planned stop; the EOD brief asks for the missing stop/setup rather than computing a bogus R.
- `setups` (name, definition, rolling stats: win rate, avg R, expectancy, sample size, active boolean)
- `risk_rules` (rule type, params, active, version): see 5.4
- `snapshots` (daily equity, open risk $, open risk %, drawdown from HWM). Equity series is flow-adjusted: deposits/withdrawals (from transactions) are excluded from HWM/drawdown math so a deposit never resets a drawdown and a withdrawal never fakes one.
- `audit_events` (append-only: approvals, rejections, collar overrides with reason, rule edits with before/after, kill-switch toggles, re-auths, shadow-mode toggles). Every mention of "logged" elsewhere in this doc means a row here.

### 5.3 Sync Jobs

- Positions + balances: every 15 min during market hours, hourly otherwise.
- Orders + transactions: every 5 min during market hours (drives journal auto-population).
- Corporate actions/dividends: from transactions feed; adjust journal cost basis automatically.
- Market data (quotes for holdings + watchlist): on demand from agent tools, cached 1-5 min. Schwab Market Data API is primary; FMP optional secondary for fundamentals/screening not covered by Schwab.
- **Market calendar:** "market hours" everywhere in this doc resolves through Schwab's market-hours endpoint (holidays, early closes), cached daily. Job schedules and blackout windows derive from it; nothing hardcodes 9:30-16:00.

### 5.4 Guardrail Engine

Rules stored as data, evaluated server-side against every `order_proposal`. Every evaluation is logged with pass/fail per rule. Starting set:

1. Max risk per trade: X% of equity (size derived from entry-stop distance).
2. Max concurrent positions; max single-position and single-sector exposure.
3. Daily loss halt and max-drawdown halt (blocks new proposals, not exits).
4. **Account-type specific (decided: cash account):** settled-cash check before any buy. Source of truth is the balances endpoint (settled cash / cash available for trading), not a local settlement ledger; the app only projects the effect of pending approved proposals on top of the broker figure. Rule is deliberately the conservative form: a buy must be fully covered by settled cash. (Buying with unsettled funds is legal if you don't sell before settlement; that path is intentionally not supported in v1 because it creates a second, time-dependent constraint on exits.) No shorting, no margin order types. PDT counter not needed.
5. Earnings/econ blackout windows for entries.
6. **Wash-sale awareness:** now a first-order tax concern, not just a flag. If a loss was realized in this account within 30 days, warn on repurchase of the same instrument in this account and in the linked IRA (an IRA repurchase disallows the loss permanently). Configurable warn vs block. Detection is instrument-match only; "substantially identical" (e.g., two ETFs on the same index) is not detected, and the doc and UI say so.
   6a. **Tax-lot awareness:** surface short- vs long-term status of lots on every proposed sell; default lot-selection method configurable (verify what lot specification the Trader API order schema supports before committing to per-order lot selection in the UI).
7. Notional cap per order and per day (fat-finger protection).

8. **Stop collar (see 5.4.1):** every entry proposal must include a stop, and the stop must fall within the computed collar or the proposal is flagged for override.

Hard rule: guardrails are enforced in Rails. The agent can read them and reason about them; it cannot bypass or edit them through MCP.

#### 5.4.1 Stop Collar Engine

Purpose: replace gut-feel stop placement with a computed acceptable range ("collar") derived from several standard methods, evaluated against price history from Schwab Market Data (FMP fallback).

Candidate methods (each produces a stop price for a proposed long entry):

- **ATR multiple:** entry − k × ATR(14), k configurable per setup (common range 2.0-3.0). The volatility-adjusted baseline.
- **Swing structure:** most recent N-bar swing low minus a small buffer (e.g., 0.1-0.3 × ATR). The "invalidated thesis" stop.
- **Percent stop:** entry − p%, p configurable (classic 7-8% max-loss discipline). The hard ceiling on distance.
- **Chandelier exit:** highest high of last 22 bars − 3 × ATR(22). Used mainly for trailing, but computed at entry for reference.

Collar computation:

- Compute all enabled methods; discard any that fail data-quality checks (insufficient history, stale quote).
- Collar = [tightest candidate, widest candidate], with the percent stop acting as an absolute floor (a stop wider than the percent method is never inside the collar).
- Proposal evaluation returns each method's value, the collar bounds, where the proposed stop sits, and the resulting position size under the max-risk-per-trade rule for the chosen stop.
- A stop outside the collar does not hard-block; it requires an explicit human override with a logged reason. (Guardrails 1-7 remain hard blocks where marked.)

Trailing behavior:

- Nightly job recomputes Chandelier/ATR trails for open positions. Where the recomputed trail is tighter than the working stop, the EOD brief surfaces a "tighten stop" suggestion with the numbers. Adjusting the actual stop order remains a human-approved action (Phase 3 candidate for auto-submit of tighten-only adjustments).

Configuration lives in `risk_rules` (method on/off, k, p, N per setup). Method parameters are data, not code, so they can be tuned as the journal accumulates evidence about which stop style fits each setup.

#### 5.4.2 Stop Order Placement (decided: real stops at Schwab)

An app-only stop with 5-15 minute polling is not protection. Every approved entry is submitted as a bracket: the entry order with a one-triggers-another child stop order (Schwab order strategies support this; confirm exact strategy type names post-approval). Consequences:

- `orders` carries `parent_order_id`; the child stop is tracked, synced, and shown on the dashboard as the working stop.
- "Tighten stop" is a cancel/replace of the child order, which goes through the proposal pipeline as a stop-adjustment proposal (guardrails: new stop must be tighter than current for the Phase 3 auto-submit class; any loosening is human-only with a logged reason).
- If the bracket child fails to place after the parent fills, the position is flagged `unprotected` on the dashboard and in a push/email immediately; this is a hard alert, not a brief item.
- Working stops are reconciled against Schwab on every orders sync; a stop that disappears at the broker (cancelled out-of-band) flags the position `unprotected`.

### 5.5 MCP Tool Surface (agent-facing)

Read tools:
- `get_portfolio` (positions with live marks, distance to stop, open risk)
- `get_account_health` (equity, settled cash, drawdown, token status)
- `get_quotes(symbols)`, `get_price_history(symbol, range)`
- `get_journal(filters)`, `get_setup_stats`
- `get_risk_rules`, `evaluate_hypothetical_order(params)` (dry-run guardrails)

Write tools (all create records; none touch Schwab directly):
- `propose_order(params, thesis, setup)` → creates order_proposal, runs guardrails, returns evaluation
- `annotate_trade(trade_id, post_mortem)`
- `add_watchlist_item(symbol, trigger)`

Explicitly absent from MCP: submit_order, cancel_order, edit_risk_rules, token operations. Submission happens only in the Rails approval UI (or a signed confirmation link), by the human.

### 5.5a Agent Runtime (where Claude actually runs)

Two runtimes, split by whether a human is present:

- **Interactive (human present):** the Claude app (desktop/Cowork/web) with the Rails MCP server registered as a remote connector. Rails exposes MCP over HTTPS with bearer-token auth (token in dokku config, rotatable). This is where ad hoc analysis, screening, and order proposals happen, billed through the Claude subscription seat.
- **Scheduled (unattended):** Solid Queue jobs on the VPS call the Anthropic Messages API directly with an API key, passing tool definitions that map to the same internal service layer the MCP server uses (in-process, no MCP hop). Output is rendered to email. This covers the 07:00 brief, 16:30 EOD, and Sunday review. **Unattended runs get read-only tools only.** These runs ingest untrusted text (transcripts, news, fetched pages), so `propose_order`, `add_watchlist_item`, and `annotate_trade` are not in their tool set; anything a brief wants to suggest is rendered as text in the email, and the human creates the proposal interactively. Write tools exist only in the interactive runtime. Each scheduled job also has a hard cap on tool turns. Rationale: unattended runs can't depend on a desktop app being open, and keeping the scheduler in Rails means the VPS is the single ops surface (one place for cron, retries, failure alerts, and the token-health gate).

Cowork Scheduled Tasks could run the unattended loops instead, but that couples automation to a second scheduler outside the VPS and to the attached-folder pattern; not used here.

One tool surface, two transports: the MCP server (remote, for the app) and the API tool definitions (in-process, for jobs) both delegate to the same service objects, so guardrails and read models cannot diverge between runtimes.

### 5.6 Memory Layer (git repo, read by agent)

Keep the file pattern from the original concept, but only for things that are genuinely human-authored strategy/context:

- `investor-profile.md`, `strategy.md`, `watchlist.md`, `prompts.md`, `instructions.md`, `edge.md` (narrative layer over setup stats)
- Removed from files because Rails owns them now: portfolio.csv, trades.csv, risk.md (risk rules live in the DB and are surfaced read-only to the agent).
- Repo is git-versioned with one writer: John. Rails never commits to it. Generated context (setup stats, edge summary) is served through the `get_setup_stats` MCP tool and injected into scheduled-run prompts at runtime, so `edge.md` stays a human-authored narrative and there is no second writer to conflict with. The VPS pulls the repo on a schedule (or post-receive hook) for the agent's read access.

### 5.8a iOS App (decided: native, private, iOS only)

- **Approach:** Hotwire Native for iOS. The Rails/Hotwire screens render inside a native shell; only the pieces that need native capability are Swift. This keeps one UI codebase and matches the house Rails conventions. No Android.
- **What the native shell adds:** APNs push, Face ID / device passcode as the deliberate confirm on Approve (resolves the open question in the flows doc: the second gesture is biometric, not a slide), app icon and home-screen presence, native navigation stack. Path configuration marks proposal detail, dashboard, and journal entry as the mobile-first routes.
- **Notifications, revised:** time-sensitive alerts move from email to push once the app exists: new proposal, fill/cancel, halt tripped, `unprotected` position, token expiring. Briefs and the Sunday ritual stay email (long-form, read on a desktop anyway). Push payloads carry no financial figures; they deep-link and the app fetches.
- **Distribution:** TestFlight internal testing (no beta review for internal testers; builds expire after 90 days, so the CI pipeline produces a fresh build on a cadence) or direct dev-signed install from Xcode. TestFlight is the default; direct install is the fallback if the developer account state makes TestFlight awkward.
- **Auth to the Rails app:** the native shell holds a session like the browser does; no separate API auth. The MCP bearer token is never on the phone.
- **Timing:** Phase 2, alongside the approval UI, since approving from the phone is the reason the app exists. Phase 1 web screens are built mobile-responsive so the native wrapper has nothing to redo.

### 5.9 Deployment (decided)

- Host: Meticulous Greencloud VPS, Ubuntu 24, deployed via dokku (matches existing Meticulous infra).
- HTTPS via dokku letsencrypt plugin; the app's OAuth callback URL is a stable route on the app's domain, registered exactly in the Schwab app config.

- **Shadow mode (Schwab has no sandbox):** a global flag, on by default in production until deliberately turned off. In shadow mode the entire pipeline runs, including human approval, but the submission step writes a `would_have_submitted` audit event and the order payload instead of calling Schwab. Playwright runs in shadow mode. Phase 2 ships with shadow mode on; it is turned off only after a stated number of shadowed approvals reconcile cleanly against what would have been sent. Toggling it is an audit event.

### 5.10 Weekly Ritual (decided: Sundays, email)

The 7-day refresh token becomes a scheduled habit instead of a surprise:

- Sunday evening email bundles: (a) the weekly edge review, (b) a re-auth link to redo the Schwab browser login, (c) system health summary (last sync times, job failures, token age).
- Re-authing every Sunday resets the 7-day clock so it never expires mid-week. Caveat: expiry is 7 days from issuance, so the email lands earlier than the prior week's auth time, and a daily health check escalates (Mon, then Tue) if the re-auth hasn't happened. On expiry, sync jobs pause and queue rather than erroring.

### 5.11 Testing & CI (mirrors Talos / Patchvault conventions)

- **RSpec** full suite: models, services, request specs. Priority coverage, in order:
  1. Guardrail engine: exhaustive unit specs per rule, including the interaction cases (CSP-style cash reservation vs GFV check is Phase 3, but settled-cash math, wash-sale window, and stop-collar bounds are Phase 1-2). Table-driven specs so each rule's edge cases are enumerable.
  2. Order proposal state machine: every legal and illegal transition (proposed → validated/rejected → approved → submitted → filled/cancelled), plus idempotency (double-submit of the same proposal must be impossible).
  3. Token lifecycle: refresh-at-25-min, 7-day expiry, degrade-and-queue behavior. Use time travel (ActiveSupport::Testing::TimeHelpers); never sleep.
  4. Schwab client service layer: VCR/WebMock cassettes only. The suite never touches the live API; cassettes get scrubbed of tokens and encrypted account values before commit.
  5. Sync jobs: fixture payloads for positions/transactions, including corporate-action and dividend events, verifying journal linking.
- **Playwright** for clickable UI: approval queue flow (approve/reject a proposal, override a stop outside the collar with a logged reason), dashboard renders with seeded data, risk-rule editor. These run against a seeded test DB with a fake Schwab adapter, not cassettes.
- **bin/ci** as the single entry point, running in order: rubocop (per DHH skill conventions), rspec, brakeman, `bin/importmap audit`, `bundle exec bundle-audit check --update`, then Playwright. Fails fast; CI green is the merge gate.
- **DHH skill** run on the codebase as a review pass: idiomatic Rails, thin controllers, no needless service-object ceremony, Hotwire-first UI. Applied at the end of each phase, not per-commit.

### 5.12 Allocation Module (cycle-pattern mechanics)

A second rule set alongside the trading guardrails, covering the book-level behaviors from post-crash market research (concentration of best days, lump-sum vs staged deployment, threshold rebalancing, correlation breakdown, leveraged-proxy discipline). Kept structurally separate from per-trade guardrails: trading rules judge one order, allocation rules judge the whole book. Both feed the same proposal → approval pipeline; nothing here auto-executes.

**Data model additions:** `allocation_targets` (asset or class, target weight, drift band), `instrument_tags` (leveraged/amplified flag per symbol), `deployment_policies` (per cash-inflow handling).

**Mechanics:**

1. **Threshold rebalancing.** Nightly drift check against `allocation_targets`. When any weight drifts beyond its band (default 5 percentage points, per-target configurable), the agent generates rebalance proposals (sell overweight, buy underweight) through the normal pipeline with guardrail evaluation. The rule is mechanical; the approval is still human. A minimum trade notional (configurable, e.g., $100) suppresses churn on a small account; drift that would require a sub-minimum order is reported, not proposed. Fractional-share support in the order API is unverified; until confirmed, quantities round down to whole shares.
2. **Leveraged-proxy exception.** Symbols tagged leveraged/amplified are excluded from mechanical rebalance proposals. Drift on those instead triggers a thesis-review task: the proposal renders the original thesis from the journal/watchlist next to current numbers, and the human decides deploy / hold / exit. Encodes "the discipline is the same, the decision is not mechanical."
3. **Deployment policy for new cash.** Cash inflows (detected via transactions sync) trigger a deployment proposal per the policy John sets in `deployment_policies` (immediate, staged over N weeks, or ask-each-time). The proposal renders the relevant base rates (lump-sum vs staged historical win rates) as context; the policy itself is John's call, stored as data, and changeable only in the rule editor.
4. **Cash-drag diagnostic.** The Sunday review computes time-in-cash vs the deployment policy and flags divergence ("policy says deployed; book is 40% cash for 3 weeks"). Informational, never a forced action.
5. **Correlation stress check.** Weekly job computes rolling 60-day correlations between each holding (and tagged "diversifier" instruments) and SPY from price history. When a diversifier's correlation exceeds a threshold (default 0.6), the Sunday review flags that the diversification assumption is currently failing. Diagnostic only.
6. **Flow/sentiment input.** Weekly fund-flow datapoint (ICI weekly long-term fund flows; source via FMP if available, else fetched from ICI's published release) rendered in the Sunday review as context alongside the edge stats. Data in, judgment human.

**Boundary:** the module surfaces mechanics and base rates; it does not embed a market view. Which patterns become policy (rebalance bands, deployment policy, what counts as a diversifier) is authored by John in the rule editor and versioned like every other rule.

**UI:** allocation targets + drift live on the dashboard below positions; rebalance and deployment proposals use the standard Flow-2 proposal detail; thesis-review proposals add the original-thesis panel. Rule authoring goes in the (desktop) rule editor.

## 6. Phasing

**Phase 1 (read-only):** Schwab OAuth + token lifecycle, account/position/transaction sync, dashboard, journal auto-population from fills, memory repo, MCP read tools, daily briefs.
**Phase 2 (propose + approve):** guardrail engine, order proposals via MCP, approval UI, bracket submission (entry + child stop, 5.4.2) from UI, ambiguous-outcome reconciliation, settlement checks from broker balances, wash-sale checks against the linked IRA, Hotwire Native iOS app with push and Face ID confirm (5.8a). Ships with shadow mode on.
**Phase 2.5 (allocation module):** targets, drift checks, rebalance/deployment proposals, correlation and cash-drag diagnostics in the Sunday review (§5.12).
**Phase 2.6 (quant research track):** forecasts frozen on proposals (horizon, probability, outcome) with Brier and reliability per setup; decision-time feature snapshots; pre-registered hypotheses with holdout dates and every variant logged; a live-vs-expected decay check in the Sunday review; costs in expectancy; an advisory skeptic note on proposals; stored daily bars and a walk-forward backtester last. Nothing in it places, sizes, or blocks an order; it produces the evidence Phase 3 is gated on. Gap analysis and open decisions: `docs/quant-research-gap-analysis.md`.
**Phase 3 (earned automation):** conditional auto-submit for a narrow class (e.g., pre-approved stop adjustments) only after the journal shows positive expectancy over a real sample; kill-switch; per-day order caps.

## 8. Options Scope (expanded from open question 2)

What "options in v1" would actually require, so the decision is informed:

**Data (resolved):** Schwab Market Data API provides option chains with greeks (delta, gamma, theta, vega, rho), implied volatility, theoretical value, and time value per contract. No local computation needed. Option symbols use OSI format (e.g., `AAPL  250117C00150000`), which touches the symbol handling everywhere: positions sync, journal linking, quotes.

**What a cash account can do (level-dependent):** long calls/puts, covered calls, cash-secured puts. No spreads without margin. Two of these create obligations the guardrail engine must model:

- **Cash-secured puts:** the engine must reserve settled cash equal to strike × 100 per contract and exclude it from "spendable" in every other proposal's GFV check.
- **Covered calls:** the engine must lock the underlying shares (can't propose selling shares that collateralize an open short call).

**Journal complexity:** R-multiple math changes (risk is premium paid for long options; assignment risk for short options). Expiration and assignment arrive as transaction events that must be linked back to the originating trade, and assignment of a CSP creates a new stock position mid-trade. This is the largest chunk of real work.

**Stop collar:** ATR/swing methods don't map to options premiums. Long options would use a premium-based max-loss rule (e.g., full premium is the risk, sized accordingly) instead of the collar.

**Recommendation:** equities-only through Phase 2. Add a Phase 3 "options module" limited to long options and covered calls first (no CSP collateral logic yet), then CSPs. Rationale: assignment/expiration lifecycle handling and collateral reservation are each roughly the size of the whole equity journal feature, and a tiny cash account gets limited benefit from CSPs anyway (collateral lockup is large relative to account size).

**Tax lots (2a, resolved):** the order object carries a TaxLotMethod field, so per-order lot method selection is possible. Default FIFO for v1; expose the method dropdown on sell proposals. Exact enum values to confirm against official docs post-approval.

None blocking. Two verify-on-approval items: exact TaxLotMethod enum values, and order-endpoint rate limits for the app config.

## 10. Risks

- **7-day refresh token** is the top operational risk; a missed re-auth silently kills all automation. Mitigated by health checks and nags, but it cannot be engineered away.
- Schwab individual-tier API terms: this is fine for personal use; anything multi-user requires their commercial review.
- Order idempotency: no client order id on the Schwab side, so dedupe is local (row-locked single submission path, `submission_unknown` state, reconcile-before-retry; see 5.1). Duplicate submission is the one bug this system cannot afford.
- Agent hallucination and prompt injection are contained by design: the agent never computes position size or submits orders, and unattended runs cannot create proposals at all (5.5a).
- Unprotected positions: bracket child failing to place or being cancelled out-of-band. Mitigated by immediate hard alert and per-sync reconciliation (5.4.2).
