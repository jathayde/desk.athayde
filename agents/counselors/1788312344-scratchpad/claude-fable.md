## Fix before commit

1. **Two recurring tasks can never enqueue.** `app/jobs/memory/pull_repo_job.rb:6` and `app/jobs/agent/sunday_review_job.rb:5` use `key: ->(*) { name }`. Solid Queue 1.7.0 evaluates that proc with `instance_exec` on the job instance (`concurrency_controls.rb:56` in the gem), and a job instance has no `name` method. The scheduler reschedules the task, then the enqueue raises `NoMethodError` into `handle_thread_error`, so the memory pull and the Sunday email silently never run in production. Specs use `perform_now`, which never computes the key. Use `self.class.name` as `BriefJob` does, and add a spec that calls `Memory::PullRepoJob.new.concurrency_key`.

2. **The 120-second request timeout is dead code.** In `resources/messages.rb:81-91` of anthropic 1.68, when the client timeout is non-default and no per-request options are passed, the SDK sets `options = {timeout: 600}`, and `base_client.rb:313` prefers that over the client value. Every call therefore has a 600-second timeout, and with two retries a hung call can hold the worker for 30 minutes. The 10-minute deadline in `run.rb:69` only runs between calls, and `AgentRun::STALE_AFTER` sweeps the row to failed at 20 minutes while the run is still live, after which `finish!` overwrites it. Pass `request_options: { timeout: Agent::REQUEST_TIMEOUT }` in `Agent::Run#call`. The `**options` spread puts a per-request value ahead of the 600.

3. **The system prompt is re-rendered on every turn, which defeats the cache.** `run.rb:73` calls `@context.system_prompt` per call, and `context.rb:38` renders fresh each time. The "Desk status as of 7:00 AM" stamp changes at every minute boundary, so the cached prefix is invalidated mid-run, and each render also shells out to git for `head_sha` twice and re-queries setup stats. Memoize `system_prompt` and `user_prompt` in `Agent::Context`.

4. **The failure digest fires on every holiday.** `AgentRun.unemailed` at `agent_run.rb:16` includes `skipped` rows, so `FailureDigest#undelivered` reports "morning brief, Mon Sep 7: skipped but never emailed (bin/rails agent:resend[…])" for both kinds on every closed day, and the resend task would then send an empty brief for a skipped run. Exclude `skipped` from `unemailed`, make `agent:resend` abort on skipped, and drop the "not emailed" flag for skipped rows on `system/show.html.erb:30`.

5. **Any exception outside `Run#perform`'s rescue means no email at all.** `Agent.client` and `Agent::Context.new` are default arguments evaluated in `Agent::Run.new` at `brief_job.rb:18`, before `perform`'s rescue. A missing `anthropic.api_key` raises `NotConfigured` there, the row stays `running`, and nothing is delivered until the digest sweeps it at 17:15. The same happens for `Anthropic::Errors::ConversionError` and any `StandardError` inside `perform`, since it re-raises and `deliver` never runs. Wrap the run in `BriefJob` so that on any exception a still-running row is finished failed with the error and delivered, then re-raise. The spec at `run_spec.rb:104` pins the re-raise, which can stay.

6. **BigDecimal renders as scientific notation.** The setups columns are `numeric`, so `system.md.erb:31` produces "win rate 0.5e0, avg R 0.12e1" and the Sunday templates print `avg_r` and `expectancy` the same way. The context spec passes because "win rate 0.5" is a substring of "win rate 0.5e0". Format with `to_s("F")` or run `setup_stats` through `Agent.serialize`, use `number_with_precision` in the mailer, and tighten the spec to the exact line.

7. **A capped run with no text becomes a failed run with a blank error.** `run.rb:132` downgrades to `:failed` without setting `error`, so the email reads "The brief is unavailable: " with nothing after the colon. Supply a reason such as "stopped by max_tokens with no text".

## What makes the first 07:00 run misleading

- **The brief races the tick.** Both tasks fire at 07:00:00. `wait_for_sync` at `brief_job.rb:32` only waits for feed runs that already have a live row, and the tick has not enqueued them yet in that same second. When the last positions sync started before about 06:29, `Dashboard#balance_stale?` is true under the in-session 31-minute threshold, so the subject reads DEGRADED with "positions are stale" and the model reads pre-sync positions while the upsert lands. Schedule the brief at `3 7 * * 1-5`, or make the wait also cover feeds that are due and not yet started. Both earlier reviews asked for this and the 90-second wait as built does not cover the common case.

- **Interim narration leads the body.** `append_text` at `run.rb:84` collects text from every response, so a brief starts with "Let me pull the portfolio and quotes." from the tool turns. The spec at `run_spec.rb:17` pins this as "Looking.\nBrief: …". For succeeded runs keep only the final `end_turn` response's text and keep the accumulation for failure paths. `retry_larger?` also clears all earlier text, so the same run yields different bodies depending on whether a `max_tokens` retry happened.

- **Quote wording.** Rule 1 says every number "carries the as_of it came with", but quotes carry `fetched_at`, `quote_time`, and `trade_time` and no `as_of`. Name `fetched_at` explicitly. The overnight-move rule itself is right: `trade_time` today means a pre-market print, otherwise "none printed yet", and stale quotes are never narrated. Rule 1 also forbids share counts while `get_portfolio` returns `quantity` and `covered_quantity`, so "partially covered" cannot say by how much. Decide whether that is acceptable.

- **The cumulative input cap counts cache reads.** A 128 KB memory repo is roughly 35k tokens per turn, so 400k cumulative fires around turn 10 regardless of tool volume and silently shortens `MAX_TURNS` as the memory files grow. Fine as a spend bound, but document it.

- **The memory pull will fail every 30 minutes on a fresh dokku mount** until the mount is owned by uid 1000 and the container has remote credentials. `safe.directory` only satisfies the ownership check. The pull writes `.git` and the working tree, and the image has no ssh key or known_hosts. An https remote without credentials fails fast with "could not read Username" because there is no tty, which is good. Each failure is a `memory_repo` sync row, so the digest carries 48 lines a day forever. The plan's fallback, a host cron pulling and the job only recording HEAD, is not implemented. Add a pull toggle or record-only mode, skip creating a run when the path is unset, set `GIT_TERMINAL_PROMPT=0`, and put a timeout on `capture2e` so a hung fetch cannot hold the worker thread.

- **Sunday re-auth link is two steps.** `SchwabController#request_authentication` at `schwab_controller.rb:43` redirects to sign-in without storing return-to, so the link lands the user on the dashboard after the magic link. Either store return-to for `authorize` only, or word the email "sign in, then System, Re-authenticate" and link System first.

## Verified correct, craft debt, and spec gaps

Cap semantics hold: the last turn is reserved because `budget_left?` uses `MAX_TURNS - 1`, the loop cannot spin because `call` raises at `MAX_TURNS` and at the deadline, a capped batch answered with `is_error` results followed by `tool_choice: none` is the shape the API expects and is thinking-compatible, the `max_tokens` retry pops the right message, and `@text` never picks up thinking blocks. The request shape is right for the gem: `system_:` maps to `system`, top-level `cache_control` is a known field, `tool_choice: {type: :none}` resolves, unknown schema keywords such as `format`, `default`, `minItems`, and `additionalProperties` pass through untouched since `strict` is not set. `ToolUseBlock#to_h` carries `caller_`, which `ToolUseBlockParam` dumps back as `caller`, and `citations: nil` on text blocks is nullable on the param model. `Anthropic::Errors::APIError` covers timeout, connection, and status errors. The unique partial index plus `served?` gives one non-failed row per kind and day, a killed worker leaves a row that the next brief or the digest sweeps, and a mail failure leaves a resendable row without a second API call. `Schwab::NoUsableToken` and `RateLimited` subclass `Schwab::Error`, so `MarketDay.for` degrades to a fallback row rather than crashing the 07:00 job. EOD sections are right: fills by `executed_at` in the New York day, journal rows by `updated_at` where only real changes bump the stamp, snapshot by `as_of` equal to the date, and the balance fallback shows its own stamp. HTML escaping is right, degraded reasons that echo tool errors are ERB-escaped, and subjects carry no dollar figures.

Craft debt:

- Subject "Athayde Desk: eod, Tue Sep 1" should humanize the kind as "end of day".
- `FailureDigest` templates print `failure.error.to_s`, which is a JSON hash. Use `exception_class` and `message`, which `SolidQueue::FailedExecution` defines. `stuck_runs` is always empty after the sweep.
- The footer says "stopped: tool_use" on a deadline failure because `@stop` is the last response's reason.
- `Brief#review_queue` and `Memory::Repo#stale?` are unused.
- Fills are not filtered to `VALID` status.
- With a 3-minute `default_concurrency_control_period`, the brief semaphore lapses before a 10-minute run ends. Irrelevant for one recurring enqueue a day, but a manual `perform_later` during a run would not be discarded.

Spec gaps:

- The fake bypasses `MessageCreateParams.dump_request`, so nothing exercises the SDK serialization of `system_`, `cache_control`, `tool_choice`, the echoed assistant content, or the tool schemas. Have `FakeAnthropic#create` run `dump_request` and JSON-encode the result before answering, and assert on `system`, `tools`, and a round-tripped `caller`.
- The fake ignores `tool_choice` and does not check that roles alternate or that every `tool_use` id is answered first in the next user message. The "stubborn" case at `run_spec.rb:65` depends on the fake violating `none`; keep it as an explicit script flag.
- No spec computes a concurrency key, pins the agent schedules, covers the digest on a skipped day, covers `BriefJob` when `Run.new` raises, covers the blank-error capped path, or asserts the per-request timeout.
