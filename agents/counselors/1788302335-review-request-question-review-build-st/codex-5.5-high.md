**Findings**

1. **Blocking: failed jobs can poison a feed forever.** [SyncRun.record](/Users/jathayde/Development/Personal/desk.athayde/app/models/sync_run.rb:16) only rescues `Schwab::Error`. Any `ActiveRecord` error, mapper bug, or unexpected nil leaves the run `running`; [due?](/Users/jathayde/Development/Personal/desk.athayde/app/models/sync_run.rb:31) then suppresses that account/feed forever. Finish the run in an `ensure`/broad rescue path, and re-raise if you want Solid Queue to record the job failure.

2. **Blocking: the tick can still grow duplicate queued jobs.** [TickJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/tick_job.rb:17) only checks started/running `sync_runs`; an enqueued-but-not-started job is invisible, so every tick can enqueue another copy. `limits_concurrency` limits execution, not enqueue volume. Add a durable pending/running lease per account/feed or a unique job key.

3. **High: partial orders runs still rewrite stop assignments.** [OrdersJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:17) detects truncation, but [assigns working stops before returning partial](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:22). Per-record quarantines also become partial only later via `SyncRun.record`. This can clear or change protection from incomplete data. Stop assignment must run only after a complete authoritative orders sync.

4. **High: first sync still cannot discover old GTC stops.** The daily `WORKING` pass is still bounded by the 59-day list window at [OrdersJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:18), and [refetch_missing_stops](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:35) only refetches stops already known locally. A real account with a 61-day-old GTC stop starts falsely unprotected. You need a verified open-orders endpoint/window or a manual import/reconciliation path.

5. **High: `Instrument.resolve` can spin forever and still races provisional rows.** The unconditional `retry` at [Instrument.resolve](/Users/jathayde/Development/Personal/desk.athayde/app/models/instrument.rb:23) loops forever if `absorb` repeatedly hits a unique CUSIP/instrument-id conflict. Separately, two symbol-only resolutions can create duplicate provisional rows because the only unique indexes are CUSIP and Schwab id. Add bounded retry plus conflict merge handling, and a provisional uniqueness key.

6. **High: one rejected activity type advances the whole activity cursor.** [ActivitiesJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/activities_job.rb:14) loops per type, but cursor state is only account/feed via [SyncRun.advanced_cursor](/Users/jathayde/Development/Personal/desk.athayde/app/models/sync_run.rb:14). A 400 for `TRADE` or `MONEY_MARKET` makes the run partial and advances `window_to`, permanently skipping that type’s rows in the window. Track per-type cursors/status, or do not advance the feed cursor for skipped types.

7. **High: journaling handoffs are missing, and nil status is treated as journalable.** The design says positions enqueue bootstrap and activities enqueue fill-linking; there are no `Journal::*` jobs referenced from [PositionsJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/positions_job.rb:26) or [ActivitiesJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/activities_job.rb:34). Also [valid_for_journal](/Users/jathayde/Development/Personal/desk.athayde/app/models/activity.rb:14) includes `nil`; the rule is only `VALID` journals.

8. **Medium: security activities can be stored without instruments silently.** [ActivitiesJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/activities_job.rb:32) allows `activity.instrument` to fail resolution and still writes a fill/dividend with `instrument_id: nil`. Cash-only rows can be null; security rows should quarantine and make the run partial.

9. **Medium: positions omit cost basis.** [PositionsJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/positions_job.rb:20) writes quantity, average price, market value, and last price, but never `cost_basis`. [Schwab::Position](/Users/jathayde/Development/Personal/desk.athayde/app/models/schwab/position.rb:3) also does not parse it. This loses a Phase 1 column on every real sync.

10. **Medium: proactive token refresh is not wired.** [Schwab.client](/Users/jathayde/Development/Personal/desk.athayde/app/models/schwab.rb:15) passes `usable_token!` directly; [ensure_fresh!](/Users/jathayde/Development/Personal/desk.athayde/app/models/schwab_token.rb:59) is never called there. The system will rely on 401 refreshes instead of refreshing ahead as designed.

11. **Low: the “daily” working pass runs twice.** [working_pass_today?](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:31) returns true only after more than one advanced orders run today, so the first two runs both include the `WORKING` pass. Use `exists?`/`>= 1`.

12. **Test blind spot: Schwab enum leakage is not caught.** [Order](/Users/jathayde/Development/Personal/desk.athayde/app/models/order.rb:2) and [OrdersJob](/Users/jathayde/Development/Personal/desk.athayde/app/jobs/sync/orders_job.rb:18) contain Schwab status/side literals outside the adapter, but [schwab_isolation_spec](/Users/jathayde/Development/Personal/desk.athayde/spec/schwab_isolation_spec.rb:5) does not search for most of them (`WORKING`, `SELL`, `VALID`, etc.). Expand that vocabulary or centralize literals fully.

**Verdict**

The fixes are directionally better than the earlier design, but this is not ready for a real Schwab account. The biggest remaining risks are stale `running` rows, duplicate queue growth, incomplete orders changing stop protection, old GTC stops missed on first sync, and activity cursor loss across per-type failures. I did not run the test suite; this was a static review against the code and specs.
