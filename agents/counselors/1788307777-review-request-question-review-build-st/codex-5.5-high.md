**Findings**

1. **High: failed-sync status can 500, and it stays visible after recovery.**  
   [app/models/dashboard.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/dashboard.rb:50) compares `run.started_at > account.last_sync(run.feed)`. If the first orders/positions run fails with a usable token and there is no successful cursor yet, `last_sync` is `nil` and the dashboard can crash. The `|| run.started_at > 1.day.ago` also keeps yesterday’s failure visible even after a newer success. Fix this as: latest failure is active only when no later successful/partial run exists, with recency as a separate display limit.

2. **High: review Save silently clears real review work.**  
   [app/controllers/trades_controller.rb](/Users/jathayde/Development/Personal/desk.athayde/app/controllers/trades_controller.rb:37) allows `setup` to be nil, and [app/models/trade.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/trade.rb:109) then clears `needs_review`. A missing-setup trade can be “reviewed” with no setup at all. It also accepts a stop at or above average entry; the view warns at [app/views/trades/review.html.erb](/Users/jathayde/Development/Personal/desk.athayde/app/views/trades/review.html.erb:12), but nothing validates it. Save must require an existing or new setup, and must reject invalid long stops with the explanatory copy rendered back on the phone.

3. **High: stop-derived numbers can show the wrong freshness.**  
   [app/models/dashboard.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/dashboard.rb:86) uses `[position.synced_at, orders_as_of].compact.min`. If a row has a working stop but no successful orders run timestamp, the UI displays only the position timestamp. That violates the “never render a market number without its age discoverable” rule because distance-to-stop depends on the stop/order feed too. If a stop participates, missing `orders_as_of` should render as `never` and stale.

4. **High: dashboard and system pages have obvious N+1s.**  
   Dashboard rows preload only `:instrument` and `:working_stop_order` at [app/models/dashboard.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/dashboard.rb:68), but `Position#protection` calls `live_stops` at [app/models/position.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/position.rb:14), repeatedly during sort, risk totals, excluded counts, and rendering. `trade_for` also queries per row at [app/helpers/dashboard_helper.rb](/Users/jathayde/Development/Personal/desk.athayde/app/helpers/dashboard_helper.rb:3). The system page queries positions/instruments per account at [app/views/system/show.html.erb](/Users/jathayde/Development/Personal/desk.athayde/app/views/system/show.html.erb:29) and sync runs per account/feed at [app/views/system/show.html.erb](/Users/jathayde/Development/Personal/desk.athayde/app/views/system/show.html.erb:45). Move this into read models with precomputed stop coverage, trade links, top symbols, and feed rows.

5. **Medium: fallback calendar handling is not honest.**  
   The dashboard checks fallback with `MarketDay.find_by` at [app/models/dashboard.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/dashboard.rb:44), but freshness calls can later invoke `MarketDay.for` through [app/models/account.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/account.rb:23) and [app/models/market_day.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/market_day.rb:44). That means a request can create/use a fallback calendar after the warning decision has already passed, and a page render can make a broker call. The UI should only read an already-known market day; the tick owns refresh/fallback creation.

6. **Medium: Sunday coverage logic is duplicated and wrong on Sunday morning.**  
   [app/views/dashboard/_banner.html.erb](/Users/jathayde/Development/Personal/desk.athayde/app/views/dashboard/_banner.html.erb:13) and [app/controllers/system_controller.rb](/Users/jathayde/Development/Personal/desk.athayde/app/controllers/system_controller.rb:14) use `next_occurring(:sunday)`, which skips today. Before 18:00 on Sunday, a token covered by today’s email is treated as if the next email is a week away. Extract the `coming_sunday_email` logic from `Schwab::TokenHealthJob` and use it everywhere.

7. **Medium: the phone header will overflow.**  
   The layout renders brand text plus Dashboard, Journal, System, and Sign out in one row at [app/views/layouts/application.html.erb](/Users/jathayde/Development/Personal/desk.athayde/app/views/layouts/application.html.erb:22). CSS gives `.shell-nav` a horizontal flex row with no wrap/collapse at [app/assets/stylesheets/application.css](/Users/jathayde/Development/Personal/desk.athayde/app/assets/stylesheets/application.css:46). On the Playwright 390px viewport this is wider than the screen. Add a compact mobile nav and an e2e assertion for no horizontal scroll.

8. **Medium: Playwright isolation is incomplete.**  
   `bin/playwright` sets the separate database correctly at [bin/playwright](/Users/jathayde/Development/Personal/desk.athayde/bin/playwright:5), but the test server does not explicitly use the test queue adapter; `SchwabToken.issue!` enqueues catch-up at [app/models/schwab_token.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/schwab_token.rb:37), so the re-auth e2e can run background sync work under the server’s default adapter. Also, scenario reset deletes many tables at [app/models/playwright/scenario.rb](/Users/jathayde/Development/Personal/desk.athayde/app/models/playwright/scenario.rb:16) but cannot clear append-only `audit_events`, so “latest audit” assertions can leak across scenarios. Make the Playwright server set `active_job.queue_adapter = :test` and avoid cross-scenario audit dependence.

9. **Medium: Skip semantics need one explicit end-state test.**  
   [app/controllers/trades_controller.rb](/Users/jathayde/Development/Personal/desk.athayde/app/controllers/trades_controller.rb:48) defers, then [next_in_queue](/Users/jathayde/Development/Personal/desk.athayde/app/controllers/trades_controller.rb:56) excludes the current trade. If the user skips the only remaining item, they land on the needs-review list where the skipped item is still present. That may be acceptable, but it is a product behavior, not an accident; add the single-item Skip case to specs/e2e.

**What Holds**

The big prerequisite fixes mostly landed: token status taxonomy exists, cash equivalents are filtered out of positions, bootstrap review does not reappear unless the plug changes, day change uses the prior snapshot by date, manual halt/resume is server-side and audited, and the Playwright route is test-only plus fake-adapter guarded.
